# SPEC-SERVICE-INTAKE-001 — Security + DPDP review

**Reviewer:** security-reviewer
**Date:** 2026-05-07

## Concerns

1. **[P1] PDF Route Handler hardening contract is under-specified.** §3 Routes and SC-6/SC-14 declare RBAC + outlet-RLS enforcement on `app/api/service/intake-inspection/[jobCardId]/pdf/route.ts`, but the spec only enumerates *what* the handler must reject (R11, cross-outlet R09). It does not enumerate the positive contract every server route MUST implement. Given this is the *only* server-rendered surface for a legally-defensible PII artefact (signature image + customer name), the spec must lock down: (a) auth/session check is the FIRST step before any store read, (b) explicit `outletId` comparison `session.user.outletId === jobCard.outletId` for non-R19+ roles, (c) per-IP / per-session rate limiting (e.g. 30 req/min) to thwart enumeration of `[jobCardId]`, (d) audit-log entry written for EVERY successful PDF download (timestamp, actorEmployeeId, jobCardId, IP, userAgent) — this is the chain-of-custody record a consumer court will subpoena, (e) deny `If-None-Match` / cache headers (PDF must be `Cache-Control: private, no-store`), (f) reject if `Origin` not in allow-list to mitigate CSRF on cookie-auth.
   **Recommendation:** Mint **L12 — PDF Route Handler hardening contract** capturing all six items above; add **SC-15** "audit-log entry written for every PDF download" + **AC-16**; add a `intake_pdf_downloaded` event row in §14 telemetry.

2. **[P1] Consent text in §13.1 is DPDP-non-compliant.** DPDP Act 2023 §6(1) requires the consent notice to specify (i) the personal data being processed, (ii) the *specific purpose*, (iii) the *manner* of withdrawal, (iv) the data principal's right to lodge a complaint with the Board, (v) contact details of the Data Protection Officer. The current footer ("This document is a vehicle condition record … Retained for 5 years per company policy and BN Automobiles DPDP notice") names the retention but does NOT cite withdrawal mechanism, DPO contact, or the principal's grievance route. Research §5.5 hand-waves this ("no new consent required beyond the service agreement") — that is a defensible legal position only if the umbrella service-agreement consent text itself satisfies §6, which is out of this spec's scope and unverified.
   **Recommendation:** Either (a) expand §13.1 to a §6-compliant notice with an explicit reference + link to the master DPDP notice and DPO email, OR (b) add an L-tag explicitly deferring to the master service agreement and cite its location + last-revision date. As written, the spec cannot move to `approved` because a reviewer cannot verify §6 compliance.

3. **[P1] DSAR pipeline (DPDP §11 data-principal access right) is mentioned but not specified.** §4 Personas lists R23 DPO with "Read-only via DSR pipeline" and §13.2 says "DSR pipeline (R23 DPO) surfaces intake records by customer," but no scenario, no AC, no test, and no selector signature exists. A customer DSAR for "all my intake records" today would force R23 to manually grep `intakeInspections` by hydrating every JC's `customerId` — there is no `selectIntakesByCustomerId` documented. Worse, the canonical id graph (§8.1) explicitly states `IntakeInspection` reaches Customer ONLY through `JobCard.customerId`, so a DSAR query is a two-hop join with no specified implementation.
   **Recommendation:** Add **SC-16** "R23 DPO retrieves all intake records for a given customerId via DSAR" + matching AC + test; add a `selectIntakesByCustomerId(customerId)` selector to §7 / store contract. This may legitimately be deferred to P4 (DEF-INTAKE-11) as long as the spec acknowledges it and DPDP §11 SLAs (Board has not yet finalized but draft rules suggest 30 days) are noted.

4. **[P1] Right-to-erasure path is missing.** DPDP §11 grants the data principal the right to request erasure. The spec correctly invokes the "lawful purpose override" via §17 of DPDP Act (5y retention for Consumer Protection Act §69 defence) — but it does NOT capture this *as a locked decision*. A future maintainer could read §13.2 and conclude erasure-on-request is unsupported. The lawful-purpose carve-out must be cited verbatim with its statutory anchor.
   **Recommendation:** Mint **L13 — Erasure deferred under DPDP §17 lawful-purpose carve-out** explicitly: "Right-to-erasure requests on `IntakeInspection` records are denied during the 5-year retention window under DPDP Act 2023 §17(1)(c) (compliance with law / legal claim defence per Consumer Protection Act §69 limitation period). Customer is informed of this exception in the consent notice (L12)." Add §13.5 "Erasure handling".

5. **[P2] `amendments[].beforeJson` / `afterJson` may leak signature data URL into audit log.** §5 IntakeInspectionSchema declares the customer signature as a top-level field on the aggregate. §6 state machine permits `amendIntake` from COMPLETED, and §5 amendments capture `beforeJson` / `afterJson` of the entire record. Nothing in the spec prevents a re-signature or correction-amendment from serializing the (PII-medium) base64 PNG into the amendment row — which then becomes effectively immutable history. CLAUDE §17 forbids PII-concatenation into logs; the audit row is functionally a log.
   **Recommendation:** L8 must be tightened: amendments MUST exclude `customerSignatureDataUrl`, `saSignatureDataUrl`, and the photo `dataUrl` array from `beforeJson` / `afterJson` — store only field names that changed plus scalar diffs. Add an explicit redaction list. Cover with a unit test asserting an amendment's `beforeJson` does not include any data URL substring.

6. **[P2] Photo PII grading is under-classified.** Slot 7 (`odometer` / dashboard with warning lights) and slot 9 (`interior` wide-angle) can readily capture: navigation screen with home/saved-locations, dashcam memory-card screen, child seats (sensitive personal data under DPDP §2(t) "personal data of a child"), personal effects (visible mail, ID cards on dashboard), parking-permit stickers identifying residence. The aggregate is graded `pii_sensitivity: medium` — defensible — but the spec's L11 grades only the *signature* as medium and says nothing about photos. R11 (Workshop Tech) gets full read on photos per the RBAC matrix §12.
   **Recommendation:** (a) Update L11 (or mint **L14**) to grade `intakeInspectionPhotos` as `pii_sensitivity: medium` — same cohort as signature. (b) Expand consent text in §13.1 to explicitly enumerate photo capture: "Ten photographs of vehicle exterior, dashboard, interior, and boot will be captured for condition documentation." (c) Add an SA training note (out-of-spec, but flagged here) that personal items visible in the interior shot should be removed before the photo. (d) PDF should NOT embed the high-res photo data URLs by default — this leaks them out of the access-controlled DMS and into a freely-shareable artefact. Currently the spec is silent on whether the PDF includes photos; if it does, that's a leak.

7. **[P2] Signature mock-phase tamperability is acknowledged neither in spec nor as a known limitation.** L11 + §5 specify `customerSignatureDataUrl` as a base64 PNG stored in service-store, which in the MSW/mock phase persists in `localStorage`. Anyone with browser dev tools can edit the PNG post-signature — invalidating the legal-defence value entirely. The user is correct that this is mock-phase only, but a reviewer cannot let this pass without an explicit "do not deploy mock to a production-ish environment" lock.
   **Recommendation:** Mint **L15 — Signature integrity in mock vs real phase**: "v1 mock-phase stores `customerSignatureDataUrl` in client-accessible state and is NOT a legally-defensible record. Mock builds MUST NOT be exposed to a customer-facing or production-adjacent environment. v1.5 backend swap-in stores the signature server-side, computes a SHA-256 digest at COMPLETED, and freezes it; amendments invalidate the prior digest and compute a new one." Add §13.6 "Mock-phase integrity caveat".

8. **[P2] §8 cross-aggregate consistency contract has a subtle race.** §8.2 row 1 says VIN's source-of-truth is Vehicle, downstream readers are JobCard + IntakeInspection, and "T13 verifies `intake.vin === jobCard.vin === vehicle.vin`." But VIN edits on `Vehicle` happen out-of-band (R19 corrections after VIN-decode error). If `Vehicle.vin` is updated *after* the intake's PDF was generated and signed, the §8 invariant holds at runtime (selectors hydrate at render) but the *signed PDF on file* now references a stale VIN, while the consistency test passes. The spec's §8.4 talks about "render-time" hydration but doesn't address: which value is canonical for the *signed historical artefact*?
   **Recommendation:** Mint **L16 — Historical artefacts are immutable snapshots of resolved values**: "When the customer signs the PDF, the rendered VIN/customerName/make/model values at that moment become part of the signed record. A subsequent change to Vehicle.vin or Customer.fullName MUST NOT silently propagate to a re-rendered PDF — instead, post-COMPLETED PDF renders MUST use the snapshot embedded in the signed-sheet attachment, not the live selector." This requires the PDF to be persisted at COMPLETED time (already implied by `signedSheetAttachmentId`). Also add SC-17 / AC-17.

9. **[P2] MV Act §130/§145 absence-vs-not-checked is conflated.** §5 declares `rcInVehicle: z.boolean()` and `insuranceCertInVehicle: z.boolean()`. A `false` value cannot distinguish "checked, not in vehicle" from "not checked at all." For a downstream consumer-court defence ("the dealer did not even verify whether documents were present"), this is a problem. Compare to `battery12VCondition` which correctly uses an enum including `NOT_TESTED`.
   **Recommendation:** Promote both fields to `z.enum(['PRESENT','ABSENT','NOT_VERIFIED'])` with default `'NOT_VERIFIED'`. This is a §5 schema change requiring spec-version bump but should land before `approved`.

10. **[P3] Intake panel auto-open + R19 skip override (§15 Q7) creates an audit gap.** The recommended resolution is "auto-open with R19 skip override" but no scenario, no event, and no audit row capture the *skip* itself. A skipped intake is the highest-risk path — the dealer has custody but no condition record.
    **Recommendation:** When Q7 resolves to YES with skip, add `intake_skipped` event with mandatory `reason` text, R19 actor, and a banner that persists for the JC's lifetime. Otherwise an SA could pressure an R19 into a one-click skip and the audit trail is silent.

11. **[P3] Telemetry `reasonHash` for `intake_amended` (§14) — hashing scheme unspecified.** A bare "hashed" reason can be reversed if the hash is unsalted SHA-256 of a typical short reason like "OCR mismatch". This is a minor concern given the reason text is not itself PII, but if it ever contains PII (an SA might paste a customer remark), it's leakable.
    **Recommendation:** Either drop the hash entirely (telemetry already excludes the raw text — that's enough) or specify HMAC-SHA-256 with a per-tenant secret. Simpler: just emit `reasonLength` instead of `reasonHash`.

12. **[P3] Open question Q4 (wheel-rim condition) has a security-adjacent angle.** Research §6.6 names rims as the #1 dispute item. If wheel-rim condition lands as a structured field in P2, it must be in the field-definitions module (L4) and inherit the same audit-trail rules as other fields. Flagging now so it isn't bolted on.
    **Recommendation:** No action in v1; note in §15 Q4 resolution that "any new structured field MUST honor L4 (field-definitions module) and L8 (amendment audit)."

## Blockers

1. **[P1 → blocker] Consent text non-compliance with DPDP §6** (Concern #2). Cannot sign off `yes` until §13.1 either expands to a §6-complete notice or explicitly defers to a verifiable master DPDP notice via L-tag.

2. **[P1 → blocker] PDF Route Handler hardening contract missing** (Concern #1). The single server-side surface for the signed PII artefact must have a locked contract before code lands. Mint L12 + SC-15 + AC-16.

3. **[P1 → blocker] DSAR + erasure paths absent** (Concerns #3, #4). DPDP §11 rights are not currently satisfiable by the spec. Either add scenarios/ACs or explicitly defer with L-tags citing statutory carve-outs.

## Open questions

1. Does the existing master DPDP notice (out of this spec's scope) already satisfy DPDP §6 — i.e., does it list signature capture, photo capture, 5-year retention, withdrawal mechanism, and DPO contact? If yes, cite it in §13.1. If no, the master notice itself must be updated before this spec can ship to production.
2. Is the PDF expected to embed the 10 intake photos? Spec is silent. Reviewer recommends NO (photos stay in DMS only; PDF prints diagram + table) to avoid PII bleed via shared / forwarded PDF copies. Author + GM signoff needed.
3. For P1 mock-phase, is there an environment-level lock preventing the mock build from being deployed to a customer-facing URL? If not, L15 (Concern #7) is necessary in the spec; if yes (e.g., env-flag check on app boot), please cite.
4. SC-9 amendment scenario uses `odometerKm` correction as the example. Should an `odometerKm` amendment ALSO require a fresh customer signature (since the original signed sheet now misrepresents the odometer)? Currently amendment requires only R19 + reason. From a CPA-2019 evidentiary standpoint, an amended condition record without re-signature has weaker weight than the original.
5. Q1 (hard-block vs soft-warn on RECEIVED→DIAGNOSED): from a security/compliance angle, the soft-warn + R19 override is acceptable IFF the override emits a permanent audit event AND the JC carries a visible "intake skipped/incomplete" badge for the entire downstream lifecycle. Confirm the audit event from L9 includes a permanent badge contract.
6. R23 DPO is granted "Read-only via DSR pipeline only" in §12 RBAC — but §12 also lists R23 in the "Create" column with a checkmark. This appears to be a typo (DPO does not create intakes). Please correct.
